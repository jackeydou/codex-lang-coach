# Dashboard 卡片复习排序方案

设计日期：2026-09-30。首期实现日期：2026-10-03。范围：插件 Dashboard 与本地网页。

建议把 Dashboard 默认顺序改为「到期复习 → 未学习 → 未到期」，由后端按全量笔记计算后分页。用户主动点击「已复习」才更新复习进度；浏览、翻页和停留都不算复习。当前阅读中的卡组顺序保持稳定，下一次打开、刷新或切换排序时使用新顺序。

## 1. 现状与首期范围

- `packages/core/src/storage.ts` 的 `getDashboardData()` 按 `created_at DESC, id DESC` 查询 SQLite；分页游标也只包含创建时间和 ID。
- `apps/worker/src/index.ts` 的 `readNotesPage()` 在 Neon 使用相同顺序和游标。
- `apps/dashboard/src/App.tsx` 的 `FlashcardDeck` 用数组下标选卡，接近末尾时加载下一页。
- `NoteFlashcard` 目前有删除操作，没有复习操作。
- 插件内嵌页通过 `McpDashboardClient` 调用本地 MCP；本地网页通过 HTTP 调用同一份 `LearningStore`。
- `RemoteLearningSync` 只上传笔记、删除记录和语言设置，不下载云端数据。云端笔记上传遇到已有 ID 时使用 `ON CONFLICT DO NOTHING`。

首期覆盖插件 Dashboard 与本地独立网页，两者共享 SQLite 中的复习状态。云端独立网页的复习功能和跨设备同步作为后续阶段；首期复习状态仅保存在当前设备，即使开启现有笔记上传也不例外。共享 React 页面根据后端能力显示复习按钮，云端未支持时继续使用时间排序。

## 2. 复习节奏

遗忘曲线和间隔学习研究提供设计方向，不能直接给每张语言卡片推算准确的记忆概率。单个「已复习」按钮也无法判断用户是否成功回忆。因此首期采用可解释的固定递增间隔；以下天数是产品默认值，不是艾宾浩斯实验给出的唯一标准。

[间隔学习研究](https://pubmed.ncbi.nlm.nih.gov/16719566/)表明，合适的间隔与希望保持记忆的时长有关。[遗忘曲线复现实验](https://pmc.ncbi.nlm.nih.gov/articles/PMC4492928/)研究了遗忘曲线的形状及不同模型。

| 本次有效学习 / 复习完成后 | 距下次复习 |
| --- | --- |
| 第 1 次：首次主动确认已学习 | 1 天 |
| 第 2 次 | 3 天 |
| 第 3 次 | 7 天 |
| 第 4 次 | 14 天 |
| 第 5 次 | 30 天 |
| 第 6 次及以后 | 60 天 |

这些间隔均从本次实际完成时间起算。例如首次周一点击，周二到期；周二再次点击，周五到期。它们不是从创建日累计的第 1、3、7 天。

规则：

1. 新卡及迁移前的历史卡统一视为「未学习」。自动生成笔记不代表用户已经读过。
2. 首次点击进入阶段 1；后续只有到期后点击才推进阶段。阶段最多为 6，之后每次有效复习仍增加计数，并安排 60 天后复习。
3. 未到期时允许继续浏览，按钮显示下次复习时间并禁用推进。服务端也拒绝提前推进，防止连点快速刷到长期阶段。
4. 逾期不会自动降级或跳级。用户晚了一周复习，仍只推进一次，从实际完成时间安排下一次。
5. 所有时间使用服务端 UTC 时间；1 天按 24 小时计算。前端按用户时区显示准确的下次复习时间。

「已复习」的含义是完成了一次学习活动，不是「已掌握」。未来如增加「忘了 / 记住了」的反馈，再设计遗忘后的短间隔和个性化调度。

## 3. 默认排序

在首次请求时固定 `asOf`，把所有有效笔记分为三组。

| 优先级 | 条件 | 组内顺序 |
| --- | --- | --- |
| 0：到期复习 | `stage > 0 && nextReviewAt <= asOf` | `nextReviewAt ASC, stage ASC, createdAt DESC, id DESC` |
| 1：未学习 | `stage == 0`，或没有复习记录 | `createdAt DESC, id DESC` |
| 2：未到期 | `stage > 0 && nextReviewAt > asOf` | `nextReviewAt ASC, createdAt DESC, id DESC` |

先完整排序，再取前 50 张；不能先取最新 50 张，再在前端排序，否则排不到更早创建的到期卡。

到期组把等待最久的卡放在前面。阶段只作为相同到期时间下的次级排序条件。首期不用未经校准的「遗忘概率分数」。

保留「最新记录」排序入口，对应原来的倒序，便于查找刚保存的笔记。默认使用「复习优先」。未到期卡保留在列表末尾，不隐藏；页面显示本轮到期数、未学习数，以及「本轮待复习已完成」提示。

例子：A 昨天到期，B 今天到期，C 刚创建，D 已复习且明天才到期。默认为 A → B → C → D。点击 A 的「已复习」后，当前卡组仍保持位置并更新 A 的状态；下一次全新请求为 B → C → 未到期组，A 在组内按新的到期时间排序。

这版采用严格优先级。到期积压较多时，新卡会靠后；用户仍可切换「最新记录」。若后续需要每日新卡配额，再引入到期卡与新卡交替，而不是首期同时增加第二套调度规则。

## 4. 数据模型

将可变的复习状态与笔记内容分开，避免修改 `createdAt` 或影响已有笔记同步。

新增 SQLite 表 `learning_note_reviews`，每张卡一条当前状态：

| 字段 | 用途 |
| --- | --- |
| `note_id` | 主键，引用笔记；删除笔记时级联删除 |
| `stage` | 0–6，调度阶段 |
| `review_count` | 有效学习 / 复习次数，含首次确认 |
| `last_reviewed_at` | 最近一次有效复习时间 |
| `next_review_at` | 下次到期时间 |
| `version` | 乐观并发版本，初始 0 |
| `algorithm_version` | 初期为 `fixed-v1`，便于后续迁移 |

未学习卡可以没有状态行，读时补默认值：阶段、计数、版本为 0，时间为 null。阶段大于 0 时要求两项时间非空。增加 `(next_review_at, note_id)` 索引。

新增 `learning_review_events`，保存每次成功操作的 `request_id`、`note_id`、`expected_version`、服务端完成时间和更新后的状态。`request_id` 唯一，存储原始响应以支持请求重试。事件随笔记删除；首期不提供用户可见的历史页或撤销功能。

Dashboard 专用类型使用 `DashboardNote extends LearningNote { review?: ReviewState }`。复习字段可选，以兼容尚未支持复习的云端和旧客户端。复习分组可按当前时间推导，不持久化。原有 `LearningNoteInput`、`list_learning_notes`、笔记创建统计保持原含义。新增独立 `reviewSummary`，不把复习次数混入「新笔记数」。

## 5. 接口与一致性

统一客户端增加：

```ts
markReviewed(input: {
  id: string;
  requestId: string;
  expectedVersion: number;
}): Promise<{
  id: string;
  review: ReviewState;
}>;
```

- HTTP：`POST /api/notes/:id/review`，请求体含 `requestId`、`expectedVersion`。
- MCP：`mark_learning_note_reviewed`，只对 App 可见；复习由用户点击触发，不让自动 coaching 代替用户确认。
- Dashboard 数据接口增加 `order: "review" | "recent"`；前端有能力时默认请求 `review`。无参数请求保留原顺序，兼容旧客户端。
- 返回 `capabilities.reviewScheduling`，共享 UI 据此启用功能。能力字段缺失时视为未支持。

服务端在同一个事务中处理：

1. 查找相同 `requestId` 的成功记录；存在且参数匹配时返回原响应，参数不同则拒绝。
2. 检查笔记存在、版本匹配及是否首次学习或已经到期。
3. 计算下一阶段、计数、时间和版本，以条件更新或插入保证仅一个请求成功。
4. 写入事件，提交事务并返回更新后的状态。

第一次写入要处理两个请求同时发现没有状态行的情况，不能只依赖前端禁用按钮。版本冲突返回最新状态，不推进；未到期返回可识别的错误及下次复习时间。不存在的笔记返回 404，不创建孤立状态。失败不生成事件。重试复用原 `requestId`，一次有效复习最多增加一次阶段和计数。

## 6. 分页与卡组稳定性

原有 `createdAt + id` 游标不能用于复习顺序。即使改成复习排序字段游标，卡片被复习后排序键改变，仍可能在翻页中重复或遗漏。

复习模式使用服务端持久化的短期卡组快照：

- 首次请求在一致的读事务内按 `asOf` 排序，保存有序的笔记 ID 和序号，生成 `sessionId`，默认有效 30 分钟。
- 快照只保存 ID 和排序位置，不复制笔记正文。
- 游标为不透明编码的 `{ sessionId, afterRank }`。后续翻页按固定序号读取，不重新计算顺序；服务端限制每页 50 张，上限 100 张。
- SQLite 保存 `review_sessions` 和 `review_session_items`，由同一数据库的 MCP / HTTP 入口共享，不依赖某个进程的内存。
- 已删除卡在读取时跳过并补足本页；游标推进到实际返回的最后一项序号。空页无后续有效卡时结束。
- 新笔记及新到期的卡等到下一次新建卡组时加入。点「已复习」只更新卡片状态，不修改快照位置。
- 过期会话返回明确错误；客户端开启新卡组、清空旧分页，并尽量按当前卡片 ID 恢复位置，不拼接两轮数据。
- 过期快照在建新会话时清理，避免无限增长。旧的时间排序继续使用原来的轻量游标。

前端按 `activeNoteId` 保持选中卡，下标只用于导航展示，避免重排后跳到另一张卡。保留现有翻页动画和加载更多逻辑；卡组更新时需要同时清理旧请求结果，避免刷新前发出的分页响应污染新卡组。

「下次请求重排」指没有游标的全新请求。带游标的加载更多继续使用本轮固定顺序。

## 7. 卡片交互

卡片底部增加固定操作区，不随正文滚动到看不见：

- 新卡显示「未学习」，到期卡显示「待复习 / 已逾期」，主按钮为「已复习」。
- 点击后显示提交状态并禁用重复点击；收到成功响应后更新这张卡的状态和下次复习时间。
- 成功后留在当前卡上，避免刚点击就跳页；用户通过现有翻页操作继续。
- 未到期卡显示「已复习 · 下次：日期时间」，禁用推进按钮。
- 写入失败时保留原状态，并在操作区给出可重试提示。网络结果不确定时复用同一请求 ID 重试。
- 翻页、键盘导航、滚动、页面曝光都不触发复习写入。
- 提供「刷新复习顺序」入口；刷新会开启新卡组，不在每次点击后全量重载。

现有界面为英文时对应使用 `Mark reviewed`、`Reviewed`、`Next review`，沿用项目语言，不局部混用中文。

## 8. 实施顺序

1. Core：补类型、纯调度函数、SQLite 表、事务化复习写入、全量排序及卡组分页。
2. Transport：本地 HTTP 和 App 专用 MCP mutation、排序参数、能力字段；两种客户端统一接口。
3. UI：复习操作区、排序切换、提交反馈、按卡片 ID 保持位置、刷新与过期会话恢复。
4. 验证后交付插件与本地网页。开发时使用隔离测试数据库，避免修改真实学习进度。

后续云端阶段：Neon 增加按用户隔离的状态、事件和卡组表，配置 RLS，并在 Worker 接入同样的调度规则。之后单独扩展同步协议，采用事件去重和服务端调度解决跨设备冲突；必须明确事件乱序及离线补传规则。只上传本地当前状态，或把两端的 `reviewCount` 相加，都不足以保证正确。要让本地反映云端复习，还需要下载复习状态的能力，这会扩展现有单向上传边界，不能默认为首期已具备。

## 9. 验收重点

- 历史卡全部按未学习处理；看过但没点击不推进。
- 首次确认安排 1 天后；后续到期点击依次安排 3、7、14、30、60 天，之后保持 60 天。
- 精确到期时可复习；提前点击、双击、请求重试、并发窗口都不能多推进。
- 超过 50 张笔记时，较早创建的到期卡仍出现在第一页。
- 到期、未学习、未到期的组顺序正确；同条件下按 ID 确定稳定顺序。
- 当前卡组复习、删除、新增笔记或跨越到期时间后，连续分页不重复、不漏掉仍存在的快照卡。
- 全新请求反映更新后的状态；旧分页响应不会混入新卡组。
- 复习写入失败不会显示为成功；服务重启后状态仍存在。
- 插件和本地网页共享进度；未支持的云端页面继续正常展示。
- 笔记统计、原有时间排序、笔记保存与上传不受影响。

上述规则已在首期代码中实现。具体验证结果见 [复习排序验证记录](dashboard-review-verification.md)。
